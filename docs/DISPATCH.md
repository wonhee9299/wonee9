# 작업 위임 프로토콜 — 폰 → 클라우드 Claude → PC Claude

**이 저장소의 모든 작업에 적용되는 기본 통로다.** 릴스 작업만이 아니다.

사용자는 폰에서 클라우드 세션에 명령한다. 클라우드 세션은 매번 새 컨테이너라
로그인된 브라우저·원본 파일·NAS·로컬 MCP 가 없다. 실제 실행이 필요한 일은 PC 세션이 맡는다.

```
사용자(폰) ─명령→ 클라우드 Claude ─┬─ 작업서를 handoff/inbox/ 에 커밋·푸시
                                   └─ 트리거로 "초인종" 발사
                                              ↓
                                        PC Claude ─실행→ 인스타 / 파일 / NAS
                                              │
                        handoff/results/ 커밋·푸시 ─┘
                                              ↓
                              클라우드가 git fetch 로 결과 확인
```

작업서를 저장소에 먼저 넣는 이유: 트리거는 단방향이고 PC 가 꺼져 있으면 도달하지 않는다.
저장소에 남겨두면 **PC 가 나중에 켜져도 밀린 작업을 찾아서 처리**할 수 있다.

---

## 클라우드 세션이 할 일

### 1. PC 세션 찾기

세션 ID 를 외우지 않는다. `list_sessions` 로 매번 찾는다. PC 워커의 표식:

- `environment_kind: "bridge"` ← 이게 핵심 (클라우드는 `anthropic_cloud`)
- `origin: "claude_code_cli"`
- `connection_status: "connected"` ← 이게 아니면 PC 가 꺼져 있다

`connected` 가 아니면 발사하지 말고, 작업서만 `handoff/inbox/` 에 넣어두고
사용자에게 "PC 가 꺼져 있어 대기 중"이라고 알린다.

### 2. 작업서 작성

`handoff/inbox/<YYYY-MM-DD>-<작업이름>.md` 에 쓴다. PC 세션은 이쪽 대화 맥락을
전혀 모르므로 **단독으로 실행 가능해야** 한다.

```markdown
# <작업 이름>
- 요청일:
- 요청자 지시 원문:

## 목표
한 문장.

## 대상
URL, 파일 경로, 계정, 식별자 등.

## 그대로 쓸 값
문안·좌표·명령어. **임의 수정 금지**라고 명시한다.

## 실행 절차
1. …

## 검증
게시 후 재조회, 블러 영역 확대 확인, 테스트 실행 등 "됐다"를 판정하는 방법.

## 하지 말 것
시도해도 안 되는 것, 건드리면 안 되는 것, 무대응할 것.

## 사용자 승인이 필요한 지점
(예: 인스타 최종 게시 버튼 — CLAUDE.md 규칙)
```

커밋·푸시한다.

### 3. 초인종 발사

`create_trigger` 에 `persistent_session_id` 로 PC 세션 ID 를 넣고 `fire_trigger`.
프롬프트는 짧게 — 작업 내용은 저장소에 있다.

> `wonee9` 저장소 `<브랜치>` 를 pull 하고 `handoff/inbox/` 의 미처리 작업서를
> 처리하세요. 규칙은 `docs/DISPATCH.md` 입니다.

### 4. 결과 확인

`git fetch origin <브랜치>` 후 `handoff/results/` 를 읽는다.
사용자가 물으면 확인해서 답한다. **아직 결과가 없으면 "진행 중"이라고만 말하고
결과를 추측해서 보고하지 않는다.**

### 5. 정리

끝난 트리거는 `delete_trigger` 로 지운다. 남겨두면 나중에 다시 발사된다.

---

## PC 세션이 할 일

작업서를 받으면 (트리거로 깨어났거나, 직접 지시받았거나):

1. `git pull` 로 최신 작업서를 가져온다.
2. `handoff/inbox/` 에서 대응하는 `handoff/results/` 파일이 없는 작업서를 처리한다.
3. 결과를 `handoff/results/<작업서와 같은 이름>.md` 에 쓴다.

```markdown
# <작업 이름>
- 상태: 완료 | 부분완료 | 실패 | 사용자입력대기
- 실행 시각:
- 한 일:
- 확인한 것: (게시 URL, 재조회 결과, 스크린샷 경로, 테스트 결과)
- 안 된 것 / 막힌 것: (원인까지)
- 다음에 필요한 것:
```

4. **커밋·푸시한다.** 이게 클라우드 세션에 결과를 알리는 유일한 방법이다.
5. 사용자에게도 짧게 보고한다.

**실패해도 반드시 결과를 남긴다.** 조용히 끝내면 클라우드 쪽은 진행 중인지 실패인지 구분할 수 없고,
사용자에게 잘못된 상태를 보고하게 된다.

---

## 전제 조건

- PC 에 Claude Code 세션이 살아 있어야 트리거가 도달한다.
  `claude remote-control` 을 띄워두거나 `/config` 의 자동 연결을 켠다 —
  `docs/reels/REMOTE_CONTROL_SETUP.md`
- PC 가 절전/종료되면 초인종이 안 울린다. 작업서는 남아 있으니 나중에 처리된다.
- 트리거로 뜬 세션은 **MCP 커넥터 없이** 실행된다. 커넥터가 필요한 작업은 이 경로로 넘기지 않는다.

## 실측 진단 (2026-08-19)

트리거 3회, 이름 지정 메시지, 환경 조회를 모두 시도한 결과:

- **트리거는 `claude_code_cli` 로 만든 유휴 SDK 세션을 깨우지 못했다** (3회 모두 무반응).
- 이름 지정 메시지(SendMessage)도 "not reachable".
- PC 는 환경(environment)으로 등록되지 않아 세션 직접 생성도 불가.
- `connection_status: connected` 는 프로세스가 릴레이에 붙어 있다는 뜻일 뿐,
  작업이 주입된다는 보장이 아니다.

**핵심 판별법**: PC 에서 `claude remote-control` 이 진짜 돌고 있으면 `list_sessions` 에
**새 bridge 세션**이 나타난다. 안 나타나면 돌고 있지 않은 것이다 (옛 세션의
connected 표시에 속지 말 것). 위임 대상은 반드시 **새로 뜬 remote-control 세션**으로 한다.

## 한계

| | 상태 |
|---|---|
| 클라우드 → PC 작업 전달 | 됨 (저장소 + 트리거) |
| PC 가 꺼져 있을 때 | 작업서는 보존, 나중에 처리 |
| PC → 클라우드 결과 회신 | 됨 (git, 클라우드가 fetch 할 때) |
| 실시간 양방향 대화 | 안 됨 |

실시간으로 주고받아야 하면 폰에서 **PC 세션을 직접 골라** 명령하는 게 낫다.
위임은 "던져놓고 나중에 확인"에 맞는 방식이다.

## 다른 저장소에도 적용하려면

이 프로토콜은 저장소의 `CLAUDE.md` 를 통해 세션에 전달된다.
클라우드 세션은 매번 새 컨테이너라 PC 의 전역 설정(`~/.claude/CLAUDE.md`)을 읽지 못한다.
따라서 **작업하는 저장소마다** `CLAUDE.md` 에 아래를 넣어야 한다.

```markdown
## 작업 위임
실행이 필요한 작업은 PC 세션에 위임한다. 프로토콜: (이 파일을 복사하거나 링크)
```

PC 쪽에는 `~/.claude/CLAUDE.md` 에 넣어두면 모든 로컬 세션이 규칙을 따른다.
